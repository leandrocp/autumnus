# LineView Decorations

Most Lumis APIs render a string directly. `LineView` is for the cases where you need the shape first: lines, spans, source ranges, line state, virtual text, and decorations that do not belong to the syntax theme.

Use it for editor views, terminal UIs, docs renderers, diff views, or custom formatters that need line data before choosing HTML, ANSI, or another output format.

## Why LineView exists

The normal highlighter output is an event stream: start a scope, copy this source range, end a scope. That is compact, and it is enough for renderers that write HTML or ANSI as they go.

Decorations need more room. A rainbow bracket is an inline style over one character. A diagnostic marker sits beside a line. A TODO marker may affect both the whole line and one span inside it. Those features are awkward in a plain token stream because they are not syntax tokens.

`LineView` sits between highlighting and formatting. Lumis still uses source text, tree-sitter queries, and highlight events underneath. `LineView` groups those facts into lines, spans, ranges, signs, virtual text, and decorations so decorators do not have to write HTML, ANSI, or renderer-specific markup.

## AST-like, not a parser AST

`LineView` is AST-like in the same practical sense as an HTML or Markdown AST: downstream code gets a stable shape to inspect before rendering.

It is not the tree-sitter syntax tree. A parser AST answers questions like "what node is this expression?" `LineView` answers formatting questions like "what should appear on this rendered line?"

That distinction matters:

- Tree-sitter trees describe language syntax.
- Tree-sitter queries describe captures such as highlights, injections, brackets, and text objects.
- Highlight events describe ordered syntax scopes over source ranges.
- Decoration output describes extra formatter-neutral data such as signs, overlays, inline styles, and line state.
- `LineView` combines those pieces into the shape a formatter actually needs.

## What LineView contains

- `Line.spans` contains highlighted source spans with byte ranges and scopes.
- `Line.line_highlights` contains whole-line state, such as selected lines or review notes.
- `Line.signs` contains short markers that sit beside a line.
- `Line.gutter_text` contains optional gutter labels for custom formatters.
- `Line.virtual_text` contains overlays attached to display columns.
- `Span.style` and `Span.decoration_kinds` contain inline decorations, such as rainbow brackets or custom review markers.

After it is built, the model is read-only. Decorators emit `DecorationOutput`; they do not mutate formatter output directly. The formatter consumes the finished `LineView` and decides how each part becomes HTML, ANSI, editor UI, or something else.

A simplified `LineView` looks like this:

```text
LineView {
    trailing_newline: false,
    lines: [
        Line {
            line_number: 1,
            range: 0..11,
            gutter_text: [],
            line_highlights: [],
            spans: [
                Span { range: 0..2, text: "fn", scopes: ["keyword.function"], ... },
                Span { range: 3..7, text: "main", scopes: ["function"], ... },
                Span { range: 7..8, text: "(", scopes: ["punctuation.bracket"], ... },
            ],
            ..
        },
        Line {
            line_number: 2,
            range: 12..31,
            gutter_text: [],
            line_highlights: [
                LineHighlight { kind: Some("review.todo"), class: Some("has-todo"), ... },
            ],
            spans: [
                Span { range: 16..23, text: "println", scopes: ["keyword.exception"], ... },
                Span { range: 23..24, text: "!", scopes: ["function.macro"], ... },
                Span { range: 25..29, text: "\"hi\"", scopes: ["string"], ... },
            ],
            ..
        },
    ],
}
```

## Annotation kinds

The `kind` fields are open-ended strings. Custom decorators can define their own labels. Built-in decorators use constants from `lumis::highlight::annotation_kinds`:

```rust
use lumis::highlight::annotation_kinds;

assert_eq!(annotation_kinds::RAINBOW_BRACKET_PREFIX, "rainbow.bracket");
assert_eq!(annotation_kinds::rainbow_bracket(1), "rainbow.bracket.1");
```

Right now the built-in decorator is rainbow brackets. Custom decorators can use reverse-DNS or app-specific labels, for example `"my_app.todo"`. More built-ins can add constants here later.

## Decoration flow

The split is simple:

- The highlighter produces syntax spans from source text and language queries.
- Decorators add line highlights, gutter text, signs, virtual text, or span decorations.
- The formatter renders the final `LineView`.

That keeps decorators portable. A decorator should not know whether the final target is terminal text, inline HTML, a docs site, or a custom review card. It emits `DecorationOutput`; the formatter decides what that looks like.

```text
source + language
  -> highlight events
  -> LineViewBuilder
  -> decorator output
  -> LineView
  -> formatter output
```

For example, a review formatter can run a decorator that finds `TODO` and `FIXME` notes. The decorator marks the relevant lines and spans. The formatter turns the same `LineView` into a code panel and an annotations column.

## Rust

The Rust builder takes source and language, runs the highlighter, applies decorators, and returns a `LineView`. The built-in decorator today is rainbow brackets. Custom decorators can emit the same `DecorationOutput`. More built-ins can use the same model later.

```rust
use lumis::highlight::{LineViewBuilder, RainbowBracketsOptions};
use lumis::languages::Language;

let source = "function main() {\n    return (1 + 2);\n}\n";

let view = LineViewBuilder::new()
    .source(source)
    .language(Language::JavaScript)
    .rainbow_brackets(RainbowBracketsOptions::default())
    .build()
    .unwrap();

assert!(view.lines.iter().any(|line| {
    line.spans.iter().any(|span| !span.decoration_kinds.is_empty())
}));
```

For custom decorators, implement `LineViewDecorator` and emit `DecorationOutput`. The formatter decides how to paint it.

```rust
use lumis::highlight::{
    DecoratorContext, DecorationOutput, LineHighlight, LineViewBuilder, LineViewDecorator,
    StylePatch,
};
use lumis::languages::Language;

struct TodoLines;

impl LineViewDecorator for TodoLines {
    fn run(&self, context: DecoratorContext<'_>, output: &mut DecorationOutput) {
        for (index, line) in context.source().split('\n').enumerate() {
            if line.contains("TODO") {
                output.line_highlights.push(LineHighlight {
                    line: index + 1,
                    kind: Some("todo.line".to_string()),
                    class: Some("todo-line".to_string()),
                    style: StylePatch {
                        bg: Some("#3a2f16".to_string()),
                        ..StylePatch::default()
                    },
                });
            }
        }
    }
}

let todo_lines = TodoLines;
let view = LineViewBuilder::new()
    .source("function main() {\n    // TODO: rewrite in Rust\n}\n")
    .language(Language::JavaScript)
    .decorators(vec![&todo_lines])
    .build()
    .unwrap();

assert_eq!(view.lines[1].line_highlights[0].kind.as_deref(), Some("todo.line"));
```

For a complete formatter example that renders custom decorator output, see [`crates/lumis/examples/custom_formatter_decorator.rs`](https://github.com/leandrocp/lumis/blob/main/crates/lumis/examples/custom_formatter_decorator.rs).

## CLI

The CLI exposes rainbow brackets through `--decorator` / `-d`:

```bash
lumis highlight main.rs --decorator rainbow-brackets
```

For now, CLI decorators render only with the terminal formatter. More built-ins can land on the same path later.

## Formatter support

A formatter that only uses `highlight_iter()` sees syntax tokens. That is fine for simple output.

A formatter that wants decorator output should render a `LineView`. Then it can decide how to display line highlights, gutter text, signs, virtual text, and span decorations.

For the full path, a custom formatter adds decorators in `prepare_line_view`, then renders the resulting `LineView`. See [Custom Formatters](/formatters/custom#supporting-lineview-decorations).

## Runtime status

Rust is the reference implementation for `LineView` and custom decorators. The CLI uses the same core model for built-in decorators. JavaScript and Elixir keep their current formatter APIs for now.
